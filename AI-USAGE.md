# AI Usage

## Overview

AI tools were used as a development assistant during this challenge. The final implementation, feature definitions, model design, evaluation methodology, and project decisions were reviewed and adapted for this specific LPDG gateway-prioritisation problem.

AI assistance was used primarily for:

- Understanding the challenge requirements.
- Planning the machine-learning pipeline.
- Discussing suitable feature-engineering approaches.
- Identifying possible data leakage risks.
- Debugging Python and PowerShell issues.
- Improving code structure and documentation.
- Reviewing evaluation methodology and results.
- Helping prepare project documentation.

---

## How AI Was Used

### 1. Problem Understanding

AI assistance was used to break down the challenge into practical implementation steps, including:

- Understanding the 15-visits-per-week constraint.
- Understanding the supplied baseline.
- Interpreting the available telemetry, meter-read, gateway metadata, and field-visit data.
- Identifying the need for a cost-based comparison against the baseline.

The final operational definition of a gateway problem was selected and implemented specifically for this challenge.

---

### 2. Feature Engineering

AI assistance was used to brainstorm and review potential features from the supplied data.

The implemented feature engineering uses a 28-day historical window and includes:

- Recent seven-day connectivity behaviour.
- Previous 21-day connectivity behaviour.
- Recent and historical disconnection counts.
- Disconnection duration.
- Offline duration.
- Reboot behaviour.
- Network and signal-quality information.
- Meter-read success statistics.
- Historical field-visit information.
- Gateway metadata.

Trend features were also introduced to capture whether gateway behaviour was deteriorating.

The final feature set was implemented and tested against the actual supplied data.

---

### 3. Machine Learning Model

AI assistance was used to compare practical machine-learning approaches and select a CPU-friendly model.

A Random Forest classifier was selected because it provides:

- Nonlinear decision boundaries.
- Good handling of mixed operational features.
- Feature importance information.
- Practical CPU performance.
- A relatively interpretable approach for this use case.

The final model configuration and preprocessing pipeline were implemented in the project and evaluated using chronological data splits.

---

### 4. Leakage Checking

AI assistance was used to identify potential target leakage during development.

An initial implementation included target-derived columns in the feature set. This was identified and corrected.

The final training pipeline explicitly excludes columns beginning with:

`target_`

This ensures that future outcome information is not directly supplied to the model during training.

---

### 5. Evaluation

AI assistance was used to design evaluation experiments covering:

- Temporal validation.
- Cost comparison with the supplied 3-Sigma baseline.
- Unseen-gateway evaluation.
- Network-change analysis.
- Feature-importance analysis.

The experiments were then executed on the supplied challenge data.

The final reported metrics and cost results are based on the actual outputs generated by the project scripts.

---

## Human Decisions

The following decisions were made specifically for this challenge rather than being automatically accepted from AI suggestions:

1. Define a gateway problem using future operational degradation.
2. Use a seven-day prediction horizon.
3. Use a 28-day historical feature window.
4. Use the previous 21 days as a comparison period for recent behaviour.
5. Rank gateways by predicted risk rather than using a fixed probability threshold.
6. Select exactly the top 15 gateways each week.
7. Use the challenge's €380 and €600 cost values for evaluation.
8. Use chronological train/validation splitting.
9. Perform a completely unseen-gateway evaluation.
10. Analyse network changes separately to understand model behaviour.
11. Produce the final `predictions.csv` according to the required submission format.

These decisions were reviewed against the available data and the operational requirements of the challenge.

---

## AI Limitations and Verification

AI-generated suggestions were not treated as ground truth.

Code and approaches suggested during development were tested against the actual project environment and data.

In particular:

- Data schemas were inspected before feature engineering.
- Gateway identifiers were normalised because different files used different identifier formats.
- Model features were checked to prevent target leakage.
- Predictions were validated using the supplied `validate_submission.py`.
- The final ML model was evaluated against later observations.
- The unseen-gateway experiment verified that test gateways had zero overlap with training gateways.
- Cost calculations were performed using the actual generated predictions and available future labels.

Where an AI suggestion was unsuitable for the available data or project requirements, it was modified or discarded.
